Adds a third plan type, "time", for selling extra days on their own.

Until now a plan was either data (type 2) or a traffic top-up (type 1), so a
user whose gigabytes were fine but whose expiry was days away had to buy a
whole new subscription. The admin plan form now offers a third type with two
pricing modes: fixed bundles (7 days at one price, 30 at another) and a per-day
rate where the user picks the number of days. Each time plan can be limited to
chosen subscription plans, or left open to all of them.

The order pipeline is encoded, so a time plan is stored as an ordinary topup
package (type 1, bandwidth 0) carrying a marker in order_note, and checkout is
the panel's own - coupon, gateway, invoice and order history all unchanged. The
days are granted afterwards by bin/timeplans.php, scheduled every minute from
TaskCommand, and timeplan_log keys on the order id so a grant happens once.
A per-day purchase first mints a package row priced at N x the daily rate;
the same row is reused for the same N, so the count stays bounded.

On the user's subscription card an "add time" button appears beside "add data",
but only near the end of the subscription - within timeplan_visible_days
(default 7), or up to timeplan_grace_hours (default 24) after it expired. Both
settings are edited in the time plan form.

The grace window needed one fix elsewhere: UserJob zeroes transfer_enable the
moment a plan expires, so buying days afterwards would have returned a working
account with no data. UserJob now records the remaining traffic in
timeplan_snapshot before wiping it, and the grant puts it back - only when the
snapshot still matches the expiry being extended.

Admin and user endpoints live in app/Patch/TimePlan.php, dispatched from
public/xmplus-patch.php (endpoint 1.2.0) ahead of its blanket admin check,
since the buying half answers ordinary users. Adds twenty-two localization keys
to en_US, fa_IR and zh_CN, and migration 004 for the two new tables.
